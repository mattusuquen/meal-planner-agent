# Design Document: AI Food Tracking & Planning Agent

**Version:** 2.1
**Author:** Matt
**Status:** Implemented (v2.1)

---

## 1. Overview

An AI-powered meal planning and nutrition tracking application. Users generate personalized meal plans and recipes via an AI agent, log meals against verified nutrition data, and monitor progress through recalculating dashboards. The core differentiator vs. generic AI tools: **nutrition accuracy backed by a real food database**, not LLM-estimated macros.

### Goals
- Generate meal plans and recipes tailored to user goals, preferences, and dietary restrictions
- Guarantee macro/calorie accuracy by grounding all nutrition data in the USDA FoodData Central database
- Provide progress dashboards that recalculate automatically as user data changes
- Surface real recipe photos and accurate recipe data via Spoonacular (no AI-generated content)
- Log meals via photo capture, free-text AI parse, USDA search, saved recipes, or meal plan

### Non-Goals (v1)
- Barcode scanning
- Wearable/fitness integrations
- Agent weekly review / adaptive calorie target revision (planned v2)
- Social features
- Native mobile apps (responsive web first)

## 3. Feature Set

### 3.1 Onboarding & Profile
- Goal selection: lose / maintain / gain weight, target rate (lbs/week)
- Biometrics: age, sex, height (ft/in), weight (lbs), activity level
- TDEE via Mifflin-St Jeor + activity multiplier; macro split 30% protein / 45% carbs / 25% fat
- Dietary preferences: cuisines, restrictions, allergies, disliked ingredients
- Meal structure: 3 meals or 3 + snacks
- Onboarding gate: middleware checks `profiles.onboarding_complete`; only redirects to `/onboarding` on first login, never on subsequent logins
- Profile saved via `upsert` so it works regardless of whether the trigger fired at signup
- Profile readable via `GET /api/profile` (used by meal plan page for goal-derived stats)

### 3.2 AI Meal Planning
- Weekly plan generated by GPT-4o-mini with profile macros as system context; `response_format: json_object`
- Day keys are local-date ISO strings (`YYYY-MM-DD` via `toLocaleDateString("en-CA")`) to avoid UTC-midnight timezone bugs
- Plan stored as JSONB in `meal_plans`; old plans archived (status = `archived`) before new plan saved
- Each `MealCell` includes: `name`, `calories`, `protein`, `carbs`, `fat`, `ingredients` (3–4 key ingredient strings), `description` (one-sentence rationale), and `image_url` (populated from Spoonacular on swap)
- Single-meal swap: Spoonacular `complexSearch` finds a real recipe within the remaining daily macro budget; result includes a real photo URL — no AI image generation
- Grocery list: aggregates `recipe_ingredients` from plan's recipe IDs, categorizes by keyword matching (Produce / Proteins / Dairy / Pantry / Grains / Other)
- Plan fetch in journal modal uses same local-date week-start calculation to match stored keys

#### Meal Plan UI (v1.2)
- **Single-day view** for all screen sizes: day-tab strip (Mon–Sun) + stacked meal cards below
- **Header:** title, goal-derived tag labels, compact week navigation
- **Macro progress rings:** 4 rings (Calories / Protein / Carbs / Fat) showing planned day totals vs. profile targets; updates when the selected day changes
- **Meal cards:** slot icon + time label + kcal + protein header; real food photo when available (from Spoonacular via swap); bullet ingredient list; description rationale card; swap button
- **Image loading:** no on-demand generation — images come from `meal.image_url` set at swap time via Spoonacular; initial plan meals generated by GPT show no image until swapped

### 3.3 Recipe System
- **Fetch pipeline (v2.1):** Spoonacular `complexSearch` filtered by user's calorie range (±25% of per-meal target), min protein, max fat, dietary restrictions, intolerances, and preferred cuisine → `getRecipeInformation?includeNutrition=true` → saved to `recipes` + `recipe_ingredients`
- Random offset (0–90 in steps of 10) + random pick within the page of 10 results ensures variety on every "Generate Recipe" call
- If no cuisine is specified, one is picked randomly from the user's `profile.cuisines` array
- Nutrition comes directly from Spoonacular's per-recipe nutrient data (divided by `servings`) — no USDA lookup needed for new Spoonacular recipes
- Real recipe photos from Spoonacular stored directly as `image_url` — no DALL-E generation, no polling, no Storage upload
- `recipes.source` now includes `'spoonacular'` in addition to `'ai'` and `'user'` (migration `003_spoonacular_source.sql`)
- `POST /api/recipes/[id]/image` (gpt-image-1 generation) is retained in the codebase but no longer called automatically; `POST /api/plan/meal-image` returns `410 Gone`

### 3.4 Food Logging
- Six entry methods: plan (one-tap from today's meal plan), recipe, USDA search, AI text parse, photo, quick-add
- Entry method stored as `entry_method` on `logged_meals`; used for accuracy weighting in future agent reviews
- After every write (INSERT or DELETE), `recalcDailyTotals` recomputes the `daily_totals` row server-side (not via DB trigger)
- Errors in `recalcDailyTotals` are caught and logged but do not fail the overall request — the meal insert still returns 200
- All POST routes upsert a profile row (`ignoreDuplicates: true`) before inserting FK-dependent rows, handling users who signed up before the migration trigger was in place

#### Custom Entry Servings Convention
All non-recipe entry methods (plan, search, text, photo, quick-add) log `servings: 1` with macros pre-scaled to the user-specified quantity. This prevents double-counting in `recalcDailyTotals`, which multiplies `custom_entry.calories × servings`. Recipe entries are the exception: they store the real servings count with `recipe_id` so `recalcDailyTotals` can fetch the per-serving value from the `recipes` table and scale it correctly.

#### USDA Search
- Search returns results with `fdcId`, `description`, `calories/protein_g/carbs_g/fat_g` per 100g
- Log entry is quantity-in-grams based (not servings), calculated from `per_100g` × grams / 100

#### Photo Logging
- Photo uploaded to `meal-photos` (private bucket) via service-role client
- Signed URL (1hr) passed to GPT-4o-mini vision; permanent URL returned to client for diary display
- Each detected item: name + estimated grams → USDA match → verified macros
- Confirmation-first UX: editable draft with confidence badges before logging

#### Text / AI Parse
- GPT-4o-mini parses free-text description into structured items (name, quantity, unit, estimated grams)
- Each item USDA-matched; same confirmation draft UI as photo

### 3.5 Progress Dashboards
- **Daily:** macro rings vs. targets, calorie budget bar, today's logged meals list; data from `/api/dashboard/daily`
- **Weekly/Monthly:** trend charts (Recharts), adherence rate, avg calories/protein; data from `/api/dashboard/trends`
- **Progress:** weight vs. calorie intake dual-axis chart; weight stats (current, total change, weekly rate)
- All reads from `daily_totals` and `weight_entries` — never sum raw logs on page load

### 3.6 Weight Tracking
- Weight entered in lbs; stored in kg (`weight_lbs × 0.453592`); displayed back as lbs
- `upsert` on `(user_id, entry_date)` — one entry per day, re-submitting overwrites
- Weekly rate: 7-day rolling average vs. prior 7-day average (lbs/week)

## 4. Data Model

```sql
profiles (
  id uuid pk references auth.users,
  goal text,                          -- 'lose' | 'maintain' | 'gain'
  activity_level text,                -- 'sedentary' | 'light' | 'moderate' | 'active' | 'very_active'
  height_cm numeric, birth_date date, sex text,
  calorie_target int, protein_g int, carbs_g int, fat_g int,
  dietary_restrictions text[], allergies text[], dislikes text[], cuisines text[],
  meal_structure text default '3_plus_snacks',
  display_name text,
  onboarding_complete boolean default false
)

recipes (
  id uuid pk, created_by uuid references profiles,
  name text, instructions jsonb,      -- array of step strings
  servings int, image_url text,
  source text,                        -- 'ai' | 'user' | 'spoonacular'
  cuisine text, prep_minutes int,
  -- denormalized verified totals per serving:
  calories numeric, protein_g numeric, carbs_g numeric, fat_g numeric,
  created_at timestamptz
)

recipe_ingredients (
  id uuid pk, recipe_id uuid references recipes on delete cascade,
  usda_fdc_id int references nutrition_cache,
  raw_text text, quantity numeric, unit text, grams numeric
)

nutrition_cache (
  usda_fdc_id int pk, description text,
  per_100g jsonb,  -- { calories, protein_g, carbs_g, fat_g }
  fetched_at timestamptz
)

meal_plans (
  id uuid pk, user_id uuid, week_start date,
  plan jsonb,   -- { "YYYY-MM-DD": { "Breakfast": MealCell | null, ... } }
  status text   -- 'active' | 'archived'
)
-- MealCell shape (stored in plan JSONB):
--   name, calories, protein, carbs, fat (numbers)
--   ingredients text[]      -- 3–4 key ingredient strings
--   description text        -- one-sentence rationale
--   image_url text | null   -- set from Spoonacular when meal is swapped; null on initial GPT-generated plan

logged_meals (
  id uuid pk, user_id uuid references profiles,
  logged_date date,
  recipe_id uuid null references recipes,
  custom_entry jsonb null,            -- { name, calories, protein_g, carbs_g, fat_g }
  servings numeric default 1,
  meal_slot text,                     -- 'Breakfast' | 'Lunch' | 'Dinner' | 'Snacks'
  entry_method text,                  -- 'plan' | 'recipe' | 'search' | 'text' | 'photo' | 'quick'
  photo_url text null,
  created_at timestamptz
)

daily_totals (
  user_id uuid references profiles,
  date date,
  calories numeric, protein_g numeric, carbs_g numeric, fat_g numeric,
  meals_logged int,
  primary key (user_id, date)
)

weight_entries (
  id uuid pk, user_id uuid,
  entry_date date, weight_kg numeric,
  unique (user_id, entry_date)
)

chat_sessions (
  id uuid pk, user_id uuid references profiles on delete cascade,
  created_at timestamptz, last_message_at timestamptz
)

chat_messages (
  id uuid pk, session_id uuid references chat_sessions on delete cascade,
  role text,               -- 'human' | 'ai' | 'tool'
  content text,
  tool_name text null,     -- populated when role = 'tool'
  tool_result jsonb null,
  created_at timestamptz
)
```

RLS enabled on all user-owned tables (`user_id = auth.uid()` or `created_by = auth.uid()`). `nutrition_cache` is publicly readable; written only via service-role client.

Auto-create profile trigger on `auth.users` INSERT — but all POST API routes also upsert the profile row defensively to handle users created before the trigger existed.

## 5. Recalculation Architecture

Daily totals are recomputed server-side (not via DB triggers) on every log write:

1. **Write-time recomputation.** Every `POST /api/log` and `DELETE /api/log` calls `recalcDailyTotals(supabase, userId, date)` after the write succeeds.
2. **`recalcDailyTotals`** fetches all `logged_meals` for that user+date, sums macros from `custom_entry` JSONB or from joined `recipes` row, then upserts `daily_totals` on conflict `(user_id, date)`.
3. **Target changes don't rewrite history.** Targets are read from `profiles` at render time and compared against stored totals.
4. **No DB triggers in v1.** Simpler to reason about; trigger-based cascade is a v2 option if write throughput requires it.

## 6. AI Agent Architecture

```
User request → Next.js API route handler
  ├── Plan generation:   LangGraph StateGraph — generatePlan → validatePlan (retry ≤1) → savePlan
  ├── Meal swap:         Spoonacular complexSearch filtered by remaining daily budget + profile prefs (swap-meal route)
  ├── Recipe generation: LangGraph StateGraph — fetchSpoonacularRecipe (search + save in one node)
  ├── Chat agent:        LangGraph createReactAgent — tool-calling loop, SSE-streamed tokens
  │     tools: get_daily_totals, get_meal_plan, swap_meal, parse_and_log_meal, confirm_log_meal
  ├── Text parse:        GPT-4o-mini → structured items → USDA match (chat parse_and_log_meal tool)
  ├── Photo analysis:    GPT-4o-mini vision (signed URL) → structured items → USDA match
  ├── Ingredient matcher: USDA /foods/search → top result → cache in nutrition_cache
  ├── Nutrition calc:    Pure TS functions in lib/nutrition.ts (no LLM involvement)
  ├── Recipe images:     gpt-image-1 (quality: low), fire-and-forget after recipe save
  └── Meal plan images:  gpt-image-1 (quality: low), on-demand per slot when day is viewed
```

- Plan generation modeled as LangGraph `StateGraph` pipeline; `recipeGraph.ts` simplified to a single `fetchSpoonacularRecipe` node (was 5 nodes: generateRecipe → lookupNutrition → calculateMacros → saveRecipe → generateImage)
- Plan generation retries once on Zod validation failure via a conditional edge (`validatePlan → generatePlan` when `attempts < 2`)
- Chat agent uses `createReactAgent` from `@langchain/langgraph/prebuilt`; bound to the 5 chat tools; response streamed via `streamEvents({ version: "v2" })`; token events filtered by `event.metadata?.langgraph_node === "agent"` to avoid streaming internal tool-call steps
- `response_format: { type: "json_object" }` on all structured generation calls; Zod validates before saving
- Recipe images: no polling, no generation — Spoonacular `image` field stored directly as `image_url` at save time
- Meal plan images: `POST /api/plan/meal-image` returns `410 Gone`; on-demand gpt-image-1 generation removed from the frontend entirely

## 9. Known Design Decisions & Gotchas

| Decision | Rationale |
|---|---|
| `toLocaleDateString("en-CA")` for all date keys | `toISOString().split("T")[0]` returns UTC date; parsing a date string without time as UTC midnight causes off-by-one day errors in non-UTC timezones |
| Service-role client for `nutrition_cache` | RLS blocks anon writes; nutrition cache is global (not per-user) so service-role is appropriate |
| Spoonacular replaces AI recipe generation | Real recipes are accurate, have real images, and produce different results every call via random offset + random pick; eliminates DALL-E cost (~$0.044/day → $0) |
| Random offset (0–90) in Spoonacular search | Without offset randomization, repeated calls with the same filters return the same first page of results; stepping the offset ensures variety on regenerate |
| `extractNutrition` divides by `servings` | Spoonacular returns `nutrition.nutrients` totals for the whole recipe, not per serving; must divide by `recipe.servings` to get per-serving values stored in `recipes` table |
| Spoonacular `complexSearch` for swap meal | Maps remaining daily budget (calories, protein, fat) directly to `maxCalories`, `minProtein`, `maxFat` query params — no LLM needed to generate a fitting meal |
| `meal-image` route returns `410 Gone` | Prevents stale client-side calls from accidentally spending on DALL-E; any client still calling it gets an explicit deprecation error |
| `structuredClone` for JSONB updates | Shallow `{ ...planRow.plan }` would share nested day-object references; `structuredClone` ensures a true deep copy before mutation |
| `gpt-image-1` quality `"low"` (retained route) | Retained for manual use; `"standard"` is rejected by gpt-image-1; valid values are `"low"`, `"medium"`, `"high"`, `"auto"` |
| `recalcDailyTotals` errors non-fatal | A failed recalculation shouldn't roll back a successful meal log; dashboard will self-correct on next load |
| Custom entries always logged with `servings: 1` | `recalcDailyTotals` multiplies `custom_entry.calories × servings`; logging pre-scaled calories with `servings: 1` prevents double-counting. Applies to plan, search, text, photo, and quick-add. Recipe entries use `recipe_id + real servings` so the DB value is multiplied correctly. |
| Profile upsert on every POST | Handles users created before migration trigger; idempotent with `ignoreDuplicates: true` |
| `ignoreDuplicates: true` on profile upsert | Prevents overwriting existing profile fields when only `id` is provided |
| In-session image persistence via `plan` state | When a storage-backed URL comes back, it is written into the React `plan` state so switching days and returning does not re-trigger generation within the same session; data URIs are intentionally excluded from this write-back (too large) |
| `serverExternalPackages` for LangChain | `@langchain/core`, `@langchain/langgraph`, `@langchain/openai` must be listed in `next.config.ts` `serverExternalPackages`; without this, Next.js attempts to bundle their ESM modules and fails at build/runtime |
| LangGraph `Annotation` requires both `value` and `default` | Every field in `Annotation.Root` that is not required input must declare both `value: (_, update) => update` (the reducer) and `default: () => ...` (the initial value); omitting `value` produces a TypeScript error even when `default` is present |
| `mapStoredMessagesToChatMessages` requires explicit `role`, `name`, `tool_call_id` | The LangChain `StoredMessage` type requires `data.role`, `data.name`, and `data.tool_call_id` fields (even if `undefined`); omitting any of them causes a TypeScript error when calling `mapStoredMessagesToChatMessages` |
| SSE token filter by `langgraph_node === "agent"` | `streamEvents` emits `on_chat_model_stream` events for both the agent's LLM calls and tool-call intermediate steps; filtering by `event.metadata?.langgraph_node === "agent"` ensures only the final reply tokens are forwarded to the client |
| `meal_draft` SSE event links tool output to the chat message | When `parse_and_log_meal` completes, the route emits a `meal_draft` SSE event; `ChatPanel` attaches it to the assistant message currently being streamed so the inline `MealConfirmCard` appears beneath that message |
| Chat `confirm_log_meal` is triggered by sending a natural-language message | After the user clicks "Log" in the `MealConfirmCard`, the panel sends a new user message (`"Yes, log all of that to my ${slot}."`); the agent receives this as a normal turn and calls `confirm_log_meal` — avoids a separate client-side confirm API call and keeps the conversation history coherent |
| Zod v4 compatible with `@langchain/core` ≥0.3 | `@langchain/core` ≥0.3.x resolves Zod schemas via `@standard-schema/spec`; no aliasing or dual-install of Zod v3 is needed when the project already uses Zod v4 |

## 10. Setup Requirements

1. Supabase project with URL + anon key + service-role key in `.env.local`
2. Run `supabase/migrations/001_initial_schema.sql` in Supabase SQL Editor
3. Run `supabase/migrations/002_chat_tables.sql` in Supabase SQL Editor (adds `chat_sessions` + `chat_messages`)
4. Run `supabase/migrations/003_spoonacular_source.sql` in Supabase SQL Editor (adds `'spoonacular'` to `recipes.source` check constraint)
5. Create Storage buckets: `recipe-images` (public), `meal-photos` (private)
6. OpenAI API key with access to `gpt-4o-mini` (and `gpt-image-1` if using the manual recipe image route)
7. Spoonacular API key — free tier at spoonacular.com/food-api; set as `SPOONACULAR_API_KEY` in `.env.local`
8. USDA FoodData Central API key (free at api.nal.usda.gov)
9. `next.config.ts` must include `serverExternalPackages: ["@langchain/core", "@langchain/langgraph", "@langchain/openai"]` to prevent ESM bundling conflicts
10. If users signed up before running the migration, run: `INSERT INTO public.profiles (id) SELECT id FROM auth.users ON CONFLICT (id) DO NOTHING;`

## 11. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Ingredient matching errors | USDA top-result matching; confirmation-first draft UX before logging |
| USDA API latency/downtime | `nutrition_cache` table; matched results cached indefinitely |
| LLM plan misses macro targets | Post-generation Zod validation; retry once; tolerance visible in plan UI |
| Recipe image generation cost | Eliminated — Spoonacular provides real photos at no extra cost |
| Meal plan image generation cost | Eliminated — `meal-image` route deprecated (410); images come from Spoonacular at swap time |
| Spoonacular free tier limit (150 req/day) | Each recipe generate = 2 calls (search + detail); each swap = 2 calls; 150/day supports ~75 generates or swaps per day per account |
| Photo portion estimates inaccurate | Confirmation draft with per-item confidence badges; macros always from USDA, never from vision model |
| Timezone date key mismatch | All date strings use `toLocaleDateString("en-CA")` consistently across client and server |
| Missing profile row (FK violation) | All write routes upsert profile defensively before insert; chat route also upserts before `chat_sessions` insert |
| Vercel function timeout on image generation | `maxDuration = 60` set on meal-image route; gpt-image-1 `quality: "low"` keeps generation fast |
| Chat agent states wrong nutrition number | System prompt forbids it; `get_daily_totals` and `parse_and_log_meal` are the only sources of numbers in chat replies |
| LLM logs meal without user confirmation | `parse_and_log_meal` returns a draft only; `confirm_log_meal` is called only after the user clicks "Log" in the confirmation card or sends an explicit confirmation message |
| Chat session FK violation on fresh users | Chat route upserts profile row before `chat_sessions` insert, same pattern as all other write routes |

The hand-rolled AI orchestration layer (raw OpenAI SDK calls, manual retry loops) has been replaced with LangChain/LangGraph. The four originally planned changes and their implementation status:

## 13. Conversational Agent — Chat (Implemented in v2)

### 13.1 Overview
A persistent chat surface available from every page. Users can ask about their plan/progress, request meal swaps, log food by description, or check remaining macros — without leaving their current view.

Not a replacement for the existing UI flows (swap button on meal cards, six-tab `AddMealModal`) — an additional entry point dispatching to the same underlying operations. The core nutrition-accuracy guarantee (Section 1) holds: the agent never states a macro/calorie number from its own knowledge; every nutrition claim must come from a tool-call result.

### 13.2 UX Placement
- **Desktop:** floating button (bottom-right); opens a `380×620px` panel anchored to the corner; also accessible from the Sidebar "Ask AI" button
- **Mobile:** "Ask AI" tab in the bottom nav bar (6th item); opens a bottom sheet (`88vh`, rounded top corners)
- Defaults to "today" context unless the user names a different date

### 13.3 Capabilities

| Capability | Example phrase | Tool(s) invoked |
|---|---|---|
| Calorie/macro check-in | "how many calories do I have left today" | `get_daily_totals` |
| Plan lookup | "what's for lunch tomorrow" | `get_meal_plan` |
| Meal swap | "swap tonight's dinner for something higher protein" | `swap_meal` |
| Log a meal | "I just had 2 eggs and toast" | `parse_and_log_meal` → (user confirms inline card) → `confirm_log_meal` |

Out of scope: generating a new 7-day plan conversationally — stays on the `/meal-plan` "Generate" flow.

### 13.4 Architecture
- `createReactAgent` from `@langchain/langgraph/prebuilt` with 5 bound tools (`lib/langchain/tools/chat.ts`)
- Each tool wraps existing lib functions — no duplicated logic
- Agent constructed per-request in `createChatAgent(supabase, userId)` (`lib/langchain/graphs/chatGraph.ts`); `supabase` client is passed in (not a singleton) to preserve cookie-bound auth
- History loaded via `SupabaseChatHistory.getMessages()` (20-message rolling window); prepended to the message list on each invocation
- Response streamed via `agent.streamEvents({ version: "v2" })`; `on_chat_model_stream` events where `metadata.langgraph_node === "agent"` are forwarded as `{ type: "token" }` SSE events
- When `parse_and_log_meal` completes with `status: "draft"`, the route emits a `{ type: "meal_draft" }` SSE event; `ChatPanel` attaches the inline `MealConfirmCard` to the currently-streaming message
- Clicking "Log" in `MealConfirmCard` sends a new natural-language message (`"Yes, log all of that to my ${slot}."`); the agent calls `confirm_log_meal` as a normal tool turn — keeps conversation history coherent
- After the stream ends, the route persists `HumanMessage` + `AIMessage` to `chat_messages` via `SupabaseChatHistory.addMessage()`

### 13.5 Data Model
See Section 4 (`chat_sessions`, `chat_messages`). Migration: `supabase/migrations/002_chat_tables.sql`.

### 13.6 API Surface
See Section 7 (`/api/chat`, `/api/chat/sessions`, `/api/chat/sessions/[id]`).

### 13.7 Design Decisions & Gotchas

| Decision | Rationale |
|---|---|
| Confirmation card before any log write | Prevents the agent from silently logging a misparsed quantity — mirrors the confirmation-first pattern in Section 3.4 |
| Tool-only nutrition facts | System prompt forbids stating any calorie/macro number not from a `tool_result` — same rule as Section 3.3 |
| `swap_meal` tool reuses route logic inline | Avoids drift between UI-triggered and chat-triggered swaps; one implementation, two entry points |
| Session-scoped rolling memory | Per-session 20-message window; durable preferences sourced from `profiles` on every turn so a changed goal can't be stale |
| `confirm_log_meal` triggered by natural-language message | Card "Log" button sends a follow-up user message; avoids a separate client-side API call and produces a logged turn in message history |
